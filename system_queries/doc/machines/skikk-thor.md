## ⚠ Active issue — suspected flaky AC-adapter connection (hardware fault, unconfirmed)

**As of 2026-08-06, three previously-separate symptoms are now suspected to share ONE root cause: an intermittent physical AC-power-sense fault (loose connector, flaky USB-C PD contact, or failing charging IC).** A live ACPI watcher caught the `ac_adapter` (device `ACPI0003:00`) event flapping online/offline in tight multi-second bursts separated by long quiet gaps — a shape consistent with a physical fault, not software polling. Each flap coincided with `battery`/`wmi` re-poll events and bursts of the known benign `NVRM: nvAssertFailedNoLog @ osapi.c:2075` assertion.

Suspected manifestations of this one fault:
- **§2.29** — AC-plugged cold-boot hangs (dies in early userspace before GPU driver load; fixed by unplugging AC and retrying). 3 occurrences (Aug 4, Aug 6 x2).
- **§2.34** — recurring hard freezes, no error signature, journal just stops. 6 occurrences in ~2 weeks (Jul 29–Aug 6); 2 of the Aug 6 freezes were immediately followed by an AC-boot-hang.
- The "double chime" reported 2026-08-06 — plausibly the OS's power-source-change notification sound firing on every flap.

**Not yet confirmed** — n=1 ~25-minute watch window, no controlled wiggle-test done, doesn't explain the pre-Aug-6 July freezes (no ACPI data available for those). **Next step: wiggle the charger cable at the connector while plugged in** to see if the flap/chime reproduces on demand (distinguishes loose connector/cable from internal IC/EC fault). If confirmed, this points to a **hardware repair/RMA path, not a software fix** — no kernel/driver change can fix a flaky physical connection; check warranty status. Full detail: `doc/skikk-thor-history.md` §2.35 (cross-references §2.29, §2.34).

## Hard constraints
- **Keep `pcie_aspm=force` with `pcie_aspm.policy=default`** — `force` is required for s2idle (PCIe root ports cannot gate power without it); `policy=default` avoids over-aggressive L1 on remaining devices. Original r8125 hard-freeze resolved by blacklisting the driver — if NIC is ever re-enabled, test `policy=default` carefully before considering `powersave`
- **This system has no `/etc/default/grub`** — GRUB is configured exclusively via `/etc/default/grub.d/` drop-ins; after any `update-grub` run, verify `/proc/cmdline` on next boot to confirm all params survived
- **BIOS updates may change the DSDT** — check NVPCF fix status after any firmware update; the current initrd override is superseded (BIOS Dec 2025 already contains the empty-method fix) and harmless but not active (kernel rejects it as OEM revision is not greater)

**NVRM `nvAssertFailedNoLog` boot assertions (2026-07-10):** 3x at ~18s post nvidia-drm init, different code path than the §2.17/§2.18 bugs, boot-only, no freeze followed. Monitoring only. Full detail: `doc/skikk-thor-history.md` §2.20.

**Firefox "downgrade" on `apt full-upgrade`, fixed (2026-07-23):** not a real regression — Ubuntu's own repo ships a snap-stub firefox with an epoch-prefixed version (`1:1snap1-...`) that always outranks the real mozillateam-PPA build in version comparison, so apt reports reverting to the PPA build as a "downgrade". `unattended-upgrades` wasn't honouring the PPA's priority-1001 pin, causing repeated ping-pong between the stub and the real build. ## Known platform quirks
- GPE07 fires ~320/sec (EC Dynamic Boost polling) — hardware characteristic, not a bug
- `ite_8291` logs 125 LED rename warnings at boot — cosmetic, RGB driver issue
- `NVreg_EnableGpuFirmware=0` in modprobe.d is silently ignored (GSP mandatory on Blackwell)
- Battery cycle count always reads 0 — EC doesn't expose wear data
- `yt6801` (Motorcomm NIC driver, TUXEDO DKMS bundle) loads and taints kernel at every boot but binds to no hardware on this chassis — cosmetic, see `doc/skikk-thor-history.md` §2.19
- `NVRM: nvAssertFailedNoLog @ osapi.c:1939` x3 at boot, ~18s after nvidia-drm init — logged-only, no freeze observed, see `doc/skikk-thor-history.md` §2.20
- **r8125/r8169 blacklisted** — `pcie_aspm=force` caused ~250 ESD recovery events/day even with no cable connected. NIC is unused (WiFi only). Blacklist at `/etc/modprobe.d/blacklist-r8125.conf`. To re-enable: `sudo rm /etc/modprobe.d/blacklist-r8125.conf && sudo update-initramfs -u -k all && reboot`.
- **io_uring/podman hung-task warnings (unconfirmed, monitoring)** — kernel hung-task warnings (ioq worker threads blocked 122–368s on mutex, kernel tainted G W OE) correlating with container creation failures (conmon exit 255) and container churn. Observed 2026-07-06 and 2026-07-09 (health-save log). Unlike the other quirks above, not yet confirmed benign/expected — watch for recurrence.
- UFW block-log volume spikes from routine LAN neighbour discovery/broadcast traffic (e.g. KDE Connect port 1716, SSDP/mDNS) are expected noise from active LAN hosts, not an attack signal
- HP USB-C dock: display and ethernet don't work (USB peripherals do) — dock uses HP's proprietary MUX alt-mode (SVID `03f0`), not standard DP Alt-Mode; HP ships no Linux driver, no fix exists. See `doc/skikk-thor-history.md` §2.22
- nvidia-open on certain GPUs (e.g. Blackwell) silently freezes on s2idle wakeup with no kernel panic or error logged — work around by setting `HandleSuspendKey=ignore` and `HandleLidSwitch=ignore` in `logind.conf`; the change is trivially reversible when the driver is fixed. Apply via reboot only — never run `systemctl restart systemd-logind` to apply `logind.conf` changes, as restarting logind terminates the graphical session and causes a hard freeze requiring physical recovery.
- `tuxedo_keyboard`/`tuxedo_io` fail to load on this chassis at all (family-26 CPU compatibility gate — see the CPU/DIMM temp creep entry in Active fixes for detail), so the daemon-owns-config rule (skill-hygiene.md: stop the daemon before writing its config) matters for `tccd` (tuxedo-control-center) specifically only if/when it becomes usable here.
- **Boot-screen hard freeze recovery procedure** — if boot hangs on the boot screen and `journalctl -b -1` shows `NVRM: nvAssertFailedNoLog: Assertion failed: !rmapiLockIsOwner() @ rmapi.c:563` right after amdgpu init: do NOT quick power-cycle repeatedly (confirmed to make it worse — each retry died progressively earlier without reaching NVIDIA init at all). Instead: (1) full power-off, hold power button 30s+ to fully drain EC/GPU state; (2) attempt a normal (non-recovery) boot — this alone resolved it 2026-08-04. If GRUB recovery (`nomodeset`) is needed as a stable fallback while investigating, it works but disables NVIDIA/GPU accel — not a long-term state. If the assertion recurs even after a full power-off, escalate: capture `nvidia-bug-report.sh` output for upstream reporting, consider a driver downgrade/reinstall. See `doc/skikk-thor-history.md` §2.28.
- `NVRM: nvAssertFailedNoLog @ osapi.c:1939` (580.126.09) / `@ osapi.c:2075` (595.84) firing repeatedly during normal desktop/GUI activity or GPU-context-creating app launches (RustDesk, Chrome) — distinct from the boot-time `rmapi.c:563` assertion, and the line number shifted with the driver upgrade (still same driver-internal debug-assertion class, not a regression). No freeze or driver malfunction accompanied either occurrence (`nvidia-smi` stayed functional throughout). Treated as benign/cosmetic pending recurrence; watch for correlation with an actual hang before escalating.
- **Early-userspace boot hang, recurring pattern, AC-correlation confirmed 2/2 — root cause not yet identified (2026-08-04, recurred 2026-08-06, monitoring)** — a boot hangs well before GPU driver load (during `systemd-modules-load`/early services), no log evidence of the cause, no panic/OOPS. Same signature on both occurrences. AC-plugged=fail / AC-unplugged=success now confirmed on both sides across both occurrences (2/2) — not proof of causation at n=2, but the leading hypothesis. Workaround: boot on battery, plug AC in after boot. Suspected EC/BIOS-level USB-C PD or AC-detection handshake stall (pattern matches known issues on other vendors); no Tongfang GM6HG7Y-specific erratum confirmed. See `doc/skikk-thor-history.md` §2.29 (2026-08-06 update).
- Guake's monitor placement is no longer done by Guake itself — its own `window.move()` is a silent no-op under native Wayland (GTK3/xdg-shell limitation, not a config bug). Placement is handled by the `guake-reposition@skikk-thor.local` GNOME Shell extension via Mutter's compositor-side `move_frame()` API, targeting monitor by connector name (`eDP-2`), not index. `display-n`/`mouse-display` dconf settings are now irrelevant/inert. See `doc/skikk-thor-history.md` §2.33.
- GNOME Shell extension code edits do not take effect via `gnome-extensions disable`/`enable` or the `ReloadExtension` D-Bus call on Wayland — GNOME Shell caches the ESM module import, so the old code keeps running until a full logout/login (no `Alt+F2 r` soft-restart exists on Wayland). Confirmed twice now (Edge `.desktop` §2.30, Guake reposition extension §2.36).
- Local `.desktop` overrides in `~/.local/share/applications/` that were hand-edited to change `Exec=` can silently lose other fields (e.g. `StartupWMClass=`) present in the vendor original — confirmed 2026-08-05 with `microsoft-edge.desktop`, which lost dock-pinning identity this way. Diff a hand-edited local override against its vendor original when touching `Exec=`. See `doc/skikk-thor-history.md` §2.30.
- This laptop's WiFi hardware is single-radio (like most laptops) — it can't stay associated to the current AP and simultaneously do full association/DHCP testing against a different target AP, since both require occupying the same radio on different channels. For AP health checks that must not drop connectivity, use a passive scan (listen for beacons only, no auth/assoc/DHCP) instead of full association testing.
