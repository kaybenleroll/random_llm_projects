# Token Economy in Claude Code — Research Report (2026-07-03)

Scope: recommendations that go BEYOND the orchestration rules already codified in `~/.claude/CLAUDE.md`. Those rules (mechanical=haiku, subagents required for research, `.scratch/` only, no nested agents, effort-level tiering) are treated as settled and are not repeated as findings here — only audited against and extended.

## Top 5 (prioritized by expected token/cost impact)

1. **Stop reflexively fanning out for small tasks.** Every `Agent` call pays a fixed overhead: a fresh context window, re-derivation of task framing, and — critically — the subagent's entire response text lands as **main-thread input tokens**. For a task a single Sonnet call could finish in <5 tool calls, delegating costs more than doing it inline. Add an explicit threshold: delegate only when the task is (a) read-heavy/mechanical (→ haiku, cheap regardless), or (b) genuinely parallelizable, or (c) would pollute main-thread context with large intermediate output. A 2-file grep-and-report task should not become a subagent.

2. **Treat compaction as a last resort, not a steady-state strategy.** Claude Code's auto-compact triggers at ~83.5% of context and produces a lossy summary — after compaction, the model re-derives context from the summary at degraded fidelity, often re-reading files it already read. The cheaper path is proactive: `/clear` at natural task boundaries, keep MEMORY.md / per-topic files as the durable record instead of relying on the live transcript, and use `/compact` manually at a chosen checkpoint (post-refactor, pre-new-module) rather than letting it fire mid-task at a bad boundary. Every auto-compact event is itself a large token spend (summarization pass) plus reduced future cache-hit rate.

3. **Prompt caching is likely being silently defeated in normal sessions and this is invisible without checking `cache_read_input_tokens`.** CLAUDE.md/skill files that change turn-to-turn (dynamic dates, unsorted structures, session-varying tool lists) sit in the cached prefix and invalidate it every turn. Given the size of the loaded context in this environment (SOUL.md, CLAUDE.md, project rules, skill files — tens of thousands of tokens), a cold cache on every turn is one of the largest and least-visible cost multipliers available. Action: periodically audit for the silent-invalidator patterns (timestamps, non-deterministic serialization, per-session tool set changes) in anything that renders before the first cache breakpoint.

4. **Right-size effort and reasoning depth per subagent call, not just per model tier.** The existing rule sets Haiku→low/medium and Sonnet→medium/high, but many Explore/haiku calls in practice request more context back than needed (verbatim file dumps instead of extracted lines). Since subagent *response text* — not internal tool calls — is what lands in the parent's context, the token cost of over-generous subagent responses is paid by the orchestrator on every single delegated call, compounding across a session far more than a single effort-level misconfiguration.

5. **Use isolation modes (worktree) sparingly — they solve a correctness problem, not a token problem, and add setup/teardown overhead.** Worktree isolation doesn't reduce token usage; it costs an extra git operation and, if the agent makes no changes, is auto-cleaned (net-zero) — but if it does produce changes, the user now has to reconcile/merge them, which is an out-of-band cost the token-economy lens doesn't capture. Reserve for genuinely parallel, mutually-interfering work, not as a default safety blanket.

## 1. Subagent orchestration patterns

**Parallel vs sequential fan-out — token cost tradeoffs.**
- Parallel fan-out (multiple `Agent` calls in one message) does not reduce total token spend versus sequential — each subagent still independently re-derives its own context and still returns response text to the parent. Parallelism buys *wall-clock* time, not *token* savings. The token cost of N parallel agents ≈ N × (per-agent context + per-agent response), same as N sequential agents, plus the parent must now hold N response payloads in context simultaneously (vs. one at a time, discarding between calls, if done sequentially with intermediate synthesis). For token minimization specifically, sequential-with-synthesis can actually be cheaper: each subagent's output gets synthesized/discarded before the next is spawned, and the parent's growing context contains only synthesized notes, not N raw dumps.
- **When fan-out is worth it despite this:** genuinely independent research questions where the answers don't need to interact, and where wall-clock matters more than token cost (e.g., time-boxed investigation). Not worth it for a task a single well-scoped agent could do — the fixed per-agent overhead (spin-up, prompt boilerplate, redundant instruction-following text like "Do NOT use the Agent tool...") multiplies linearly with agent count.
- **Avoiding redundant context re-derivation across subagents:** the current rule (include exact file paths, line numbers, what to change) is the right lever — subagent prompts that say "based on the research above" force the subagent to either ask for it (round trip) or guess. Every subagent should get a **self-contained** brief; the cost of writing that brief in the main thread is far smaller than the cost of a subagent re-exploring the codebase.
- **Isolation mode (worktree) cost implications:** creates a new git worktree — cheap in wall-clock, free in tokens directly, but shifts cost onto reconciliation (the user or a follow-up agent must merge/inspect the branch). Auto-cleanup on no-change is a real token-and-time saver for exploratory work that might not pan out — use it when you're not sure the subagent's changes will be wanted, since a clean revert costs nothing.

**Recommendation:** default to a **single capable agent doing more** unless the task decomposes into truly independent units or unless keeping the main thread's context clean is itself worth the delegation overhead (this is often the dominant real reason to delegate — not parallelism, but context hygiene).

## 2. Model tiering

The haiku/sonnet/opus split (mechanical=haiku, reasoning=sonnet, opus=explicit escalation) is directionally correct and matches Anthropic's own documented guidance (`effort` matters more than model choice at the margin; lower-tier models with well-scoped prompts often match higher-tier models with vague ones). Refinements:

- **Haiku 4.5 is capable enough now to take more of the "medium" synthesis workload than teams typically route to it.** The existing cap (Haiku synthesis → "medium" max) is reasonable, but many tasks currently defaulting to Sonnet — simple classification, short-answer extraction, single-file code review for style-only issues — are haiku-appropriate. Consider adding a rule: "single-file, single-concern review/extraction tasks default to Haiku unless the file is unusually complex or ambiguous."
- **Sonnet 5 is a meaningfully better default than Sonnet 4.6 for the same price tier** (near-Opus quality on coding/agentic work, `xhigh` effort available). Given the current pricing table shows Sonnet 5 with an introductory discount through 2026-08-31 ($2/$10 vs sticker $3/$15), this is a good window to shift Sonnet-tier subagent work onto Sonnet 5 rather than 4.6 if not already done — better quality per token *and* temporarily cheaper.
- **Fable 5 does not fit this orchestration model at all and should stay excluded from the tiering ladder.** It's priced above Opus ($10/$50), always-thinking, and designed for long-horizon autonomous runs (single requests can take 15+ minutes). Using it as a "biggest hammer" escalation for subagents defeats the point of subagent orchestration (many bounded, cheap, parallel-friendly calls) — it belongs at the *session* level (e.g., an overnight autonomous Claude Code run), not as a subagent tier. The existing rule correctly omits it; keep that.
- **Opus 4.8 vs 4.7 vs 4.6 as the "explicit escalation" tier:** default to 4.8 (no new breaking changes vs 4.7, same cost, better long-horizon coherence and narration control). No orchestration-rule change needed — just make sure any hardcoded `model: "opus"` references resolve to 4.8, not an older pinned Opus alias, since older aliases remain functional but are strictly dominated.
- **Effort refinement beyond the existing ladder:** for Sonnet-tier subagents doing bounded implementation, the existing "medium" default is right, but tasks that are bounded *and* mechanical-adjacent (e.g., "apply this exact diff pattern to 5 files") should use `low` even on Sonnet — effort, not just model, is the lever that most changes tool-call verbosity and preamble length, and low-effort Sonnet is often cheaper AND faster than medium-effort Sonnet for narrow, well-specified work.

## 3. Context management: compaction, pruning, and memory

**How/when compaction triggers, and what it costs.**
- Claude Code auto-compact currently triggers around ~83.5% of the context window (recently tightened from ~77-78%), leaving a smaller live buffer (~33K tokens / 16.5%) than in earlier releases — meaning auto-compact fires later and more abruptly than it used to.
- Compaction is not free: it's a full summarization pass over the existing transcript (billed as an additional generation), and the resulting summary is lossy — subsequent turns may re-read files or re-derive facts that were compacted away, effectively re-paying for information the session already had.
- At the API level (distinct from Claude Code's own compaction), the `compact-2026-01-12` beta mechanism requires echoing back the full `response.content` (including compaction blocks) on every subsequent turn — dropping this silently breaks the compacted state. This is Claude Code's internal mechanism, not something this session controls directly, but it's useful background for reasoning about *why* compaction has a token cost beyond "it summarizes."

**Auto-compaction vs proactive pruning vs memory system.**
- **Auto-compaction** is a safety net, not a strategy. Relying on it means the session runs "hot" (near the context ceiling) for long stretches, which also *degrades cache-hit rate* — a growing, soon-to-be-discarded transcript is exactly the kind of prefix that's about to be invalidated wholesale.
- **Proactive pruning** (`/clear` at task boundaries, `/compact` at a *chosen* checkpoint rather than the forced one) is strictly better when available: the user controls where the summarization boundary falls (post-refactor, pre-new-module), rather than compaction firing mid-task at an arbitrary point that produces a worse summary.
- **The memory system (MEMORY.md + per-topic files) reduces the *need* to keep things in the live transcript at all**, which is a different and more powerful lever than compaction: information written to memory persists **outside the token-billed context** entirely. A fact in MEMORY.md costs tokens only when explicitly loaded (typically once, at session start, as part of the system/CLAUDE.md context) — not on every turn as part of a growing transcript. This means: **the more that's durably true and reusable across sessions gets written to memory promptly (as this session's own workflow already does via the `reflect` skill and feedback files), the less that same information needs to survive in-transcript until an eventual costly compaction.** Concretely: a decision made in turn 5 that's still relevant in turn 80 either (a) survives 75 turns of transcript un-compacted (cost: counted every turn, and at risk of being lossy-summarized), or (b) gets written to a memory file once and dropped from working context, to be re-loaded cheaply (once) in a future session. Option (b) dominates on tokens whenever the fact needs to survive past the current context window's effective lifetime.
- **Practical rule:** if something is worth remembering past the current task, write it to memory/notes *and drop it from active reasoning* rather than trusting it to survive in-transcript until compaction. This is already partially captured by "Notes and findings go in notes/" in this project's CLAUDE.md — the refinement is to apply it *within* a session, not just across sessions: promote durable facts out of the live transcript proactively rather than waiting for the memory-write to happen only at session end.

## 4. Other cost-control levers

**Prompt caching mechanics — maximizing hits.**
- Caching is a strict prefix match: `tools` → `system` → `messages` render order, and any byte change anywhere in that prefix invalidates everything after it. Practical implications for Claude Code sessions specifically:
  - CLAUDE.md / SOUL.md / skill files are part of the system-prompt-equivalent prefix loaded at session start. If any of these files are edited mid-session (e.g., via `reflect` or `claude-md-management` skills), the cache is invalidated for the remainder of that session — the next turn pays full input-token price for the entire accumulated system context. **Avoid editing config files mid-session if the session is expected to continue for many more turns; batch such edits at session boundaries instead.**
  - Minimum cacheable prefix is model-dependent (4096 tokens for Opus-tier, 2048 for Sonnet 4.6, lower for older models) — a short system context won't cache at all regardless of markers.
  - Session structure that maximizes hits: keep the early part of the transcript (system prompt, skill loads, tool definitions) byte-stable for as long as possible; put anything session-specific or turn-varying as late as possible in the rendered prompt.
  - **Verification, not assumption:** cache hit rate isn't visible in the Claude Code UI the way it is via the raw API's `usage.cache_read_input_tokens` field. There's no direct lever in this session to inspect it, but the same silent-invalidator patterns apply (dynamic timestamps, non-deterministic ordering) — worth being aware that "the environment context includes today's date" (as it does, injected at the top of every session) is itself a value that could vary and is exactly the kind of prefix element that, if it changes turn-to-turn within a session (it shouldn't, but any per-turn-injected variable would), silently defeats caching for everything after it.

**Effort-level tuning beyond the existing ladder.**
- Already covered under Model Tiering above — the key addition is: effort is a bigger token lever than most people budget for. Dropping from `high` to `medium` effort on a bounded Sonnet task often cuts token spend more than dropping a model tier, because effort directly controls thinking-token volume, tool-call consolidation, and preamble verbosity — three of the largest "invisible" cost centers in agentic loops.

**Workflow tool cost model.**
- Claude Code's dynamic workflow / multi-agent fan-out feature caps concurrency at 16 agents by default with a hard ceiling of 1,000 agents per run, and supports an explicit token budget (settable by plain instruction, e.g. "use 10k tokens for this workflow") that the model self-moderates against via a running countdown — conceptually the same mechanism as the API's `task_budget` parameter (`output_config.task_budget`, beta, minimum 20,000 tokens per the API — Claude Code's plain-language budget-setting is a simplified wrapper over the same idea).
- **Cost implication:** 1,000 potential agents is a ceiling, not a target — a wide fan-out at Sonnet/Opus rates is real money even with the 16-concurrent throttle, since total spend is bounded by agent count × per-agent cost, not by concurrency. Treat the default 16-concurrent cap as a *feature* (keeps a workflow from silently ballooning cost), not an obstacle to push past. When using a Workflow, set an explicit token budget for anything with an unbounded or uncertain fan-out shape (e.g., "process every file matching X") rather than letting it discover the full scope mid-run.

**When NOT to use subagents at all.**
- Small/simple tasks where the delegation overhead exceeds the savings: single-file reads, single targeted greps, quick lookups the main thread could do via the allowed tools directly for that immediate turn only when it's not "research" per the hard rule (note: the hard rule bans Read/grep in the main thread *for research* — a single-purpose lookup that's part of *this* subagent's own bounded task, executed from inside a subagent, is fine and expected). At the orchestration level: don't spawn a subagent to answer something already fully specified in the current context (e.g., re-deriving a fact already in MEMORY.md or already stated by the user) — this is pure waste, since the subagent's context-building costs more than just using what's already available.
- A task that requires only 1-2 tool calls to resolve is nearly always cheaper done as a single Bash/Read/WebFetch/WebSearch call from whichever agent already has the necessary context loaded, rather than spun out to a fresh agent that must first re-establish that context.

**CLAUDE.md / skill file bloat as a hidden token tax.**
- Every CLAUDE.md, SOUL.md, and skill file loaded at session start is paid **on every single turn** for the remainder of the session unless it falls entirely within a stable, cached prefix (see caching section above) — and even when cached, it still counts toward the context-window budget that eventually forces compaction.
- The `claude-api` skill alone, as loaded in *this* session, is enormous (tens of thousands of tokens across every language's README, managed-agents docs, etc.) — this is the single largest concrete token cost visible in this very conversation. Its trigger conditions are broad (any mention of Claude/Anthropic/model names), which means it fires on more sessions than strictly need the full reference. **Actionable check:** confirm whether the `claude-api` skill's trigger phrasing is broader than needed for this project's actual use cases (research/orchestration commentary vs. actually writing SDK code) — if this project rarely writes Anthropic SDK code directly, a narrower trigger (or splitting the skill so only the `claude-api` reference doc quick-reference sections load, not every language's full README) would meaningfully cut the fixed per-session tax.
- More generally: `reflect-maintain` (already in the skill list) exists precisely to catch this — periodically compress/de-duplicate/demote CLAUDE.md and skill content as it accumulates. This should be run on a cadence tied to noticeable config growth, not left until context rot is already causing problems; the earlier it runs, the cheaper every subsequent session becomes, compounding across all future sessions (unlike most of the levers above, which are per-session, this one is a fixed cost paid by *every* future session until fixed).

## Community findings

Researched via the playbook in `research-sources-checklist.md` (HN Algolia API, GitHub issue search on `anthropics/claude-code`, and WebSearch-surfaced practitioner blogs — direct Reddit access is blocked for Anthropic's crawler, confirmed via an explicit API error, so Reddit signal here is second-hand via articles that reference it). Findings below are tagged **AGREES** / **DISAGREES** / **NEW** relative to the codified rules and the analysis above.

**Subagent cost reality checks (AGREES, with sharper framing).**
- KDnuggets and a Substack cost-optimization guide both independently converge on the same framing already used in §1 above: *"subagents are not automatically cheaper... use subagents when the saved main-context clutter is worth more than the startup overhead."* This is a strong practitioner-side confirmation that "delegate for context hygiene, not just parallelism" is the right mental model, not just a theoretical one.
- A GitHub-surfaced comment thread (via HN discussion on a context-tooling launch) reports a concrete failure mode not covered above: **"Claude Code subagents often re-read the same files and rebuild the same context from scratch"** — i.e., redundant context re-derivation happens *across* subagents in the same session, not just within one. One developer built a file-overlap tracker specifically to route new work to an existing subagent instead of spinning up a fresh one that re-reads what a sibling agent already read. **NEW, actionable:** when multiple subagents in the same session are likely to touch overlapping files, consider explicitly telling later subagent prompts what earlier ones already found/read (a short "prior agent X already established Y" note) rather than assuming isolation is free — this is the same "avoid redundant re-derivation" principle already in the codified rules, but the community evidence shows it also applies *between* sibling subagents in one session, not only between main-thread and subagent.

**CLAUDE.md size (AGREES, with a concrete number).**
- Independently confirmed across three sources (KDnuggets, Analytics Vidhya, a GitHub-linked drop-in "claude-token-efficient" tool): a large CLAUDE.md is a *per-turn* tax, with KDnuggets stating plainly: *"a 5,000-token CLAUDE.md costs 5,000 tokens on every single turn."* Analytics Vidhya's practitioner guide recommends keeping the **global** CLAUDE.md under ~200 lines and pushing subsystem-specific guidance into `.claude/rules/` (path-scoped, loads only when relevant files are touched) — this directly validates the report's §4 recommendation to audit skill/CLAUDE.md bloat, and gives a concrete target (200 lines) worth adopting as a soft ceiling when auditing this environment's own CLAUDE.md/SOUL.md/skill files.

**Compaction — practitioner behavior goes further than official guidance (NEW / partially DISAGREES with "let auto-compact be a safety net").**
- Analytics Vidhya's guide describes practitioners **overriding the auto-compact trigger threshold downward** via an environment variable — `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=70` for normal work, `50` for "noisy" workflows — rather than letting Claude Code's own ~83.5% default threshold govern. The stated rationale: compacting earlier, before context is nearly exhausted, produces a cleaner, less lossy summary than compacting under pressure at the ceiling. **This flags a gap in the report's §2 recommendation** ("treat compaction as a last resort" / rely on manual `/compact` at chosen checkpoints) — community practice goes a step further by *lowering the automatic trigger itself* rather than only manually triggering early. **Caveat: this env var was not independently verified against official Anthropic documentation in this pass** — flag as a community-sourced claim to verify before recommending it be adopted, not as confirmed API/CLI behavior.
- KDnuggets independently converges on the same "compact early, not at the warning line" principle without the env var: *"compact your session early, while still healthy, rather than waiting until context warnings appear... early compaction produces cleaner summaries."* This part is corroborated by two independent sources and is a safe, low-risk refinement to adopt: prefer `/compact` at your own chosen checkpoint *well before* the auto-compact threshold, not just "before it forces you."
- GitHub issue-search surfaced real user pain that supports treating compaction as strictly worse than avoiding it: a 176-comment thread on auto-compact reliability bugs, a 134-comment thread on "Error during compaction," and — most relevant to the memory-vs-compaction argument in §3 — a 61-comment **open feature request**, "Persistent Memory Across Context Compactions," from a user who logged **59 compactions across 26 days** of heavy daily use and, finding no built-in persistent-memory mechanism, built one by hand: a 3-tier system (an always-loaded `MEMORY.md` under ~100 lines, on-demand topic files, and a large synced vault) plus a `compaction_watcher.py` script that logs every compaction event with a timestamp and "the user's last words before context was lost." **This is strong independent validation of §3's core claim** — that writing durable facts to memory *before* compaction forces them out is cheaper and more reliable than trusting compaction to preserve them — and it shows real users are already building exactly the MEMORY.md-plus-topic-files pattern this project's own memory system already follows, but doing so ad hoc and under duress rather than as a designed default.

**Pre-filtering command output before it enters context (NEW — not covered in the original 4 sections).**
- Analytics Vidhya's guide surfaces a concrete pattern this report didn't originally cover: pipe verbose command output through `grep`/`head` *before* it reaches Claude's context, e.g. `pnpm test 2>&1 | grep -A 5 -E "FAIL|ERROR|Error|failed" | head -120` rather than letting a full raw test-run log flood the transcript. This is a direct, low-risk lever distinct from subagent delegation or caching — it applies even to single-agent, non-delegated work, and is arguably higher-leverage for routine dev-loop tasks (running tests, builds, linters) than any of the subagent-tuning advice above, since raw tool output is often the single largest per-turn token cost in ordinary coding sessions.

**Cost/quota complaints suggest token accounting has real variance beyond what any prompt-engineering lever controls (NEW, tempering caveat).**
- GitHub issue search surfaced multiple open/high-engagement bug reports describing quota exhaustion that the reporters could not attribute to their own usage patterns — e.g. issue #42052 ("Max 20x plan: 100% usage after 2 hours of light work, 5 commits, no subagents") and a related cluster of issues (#38335, #38357, #37394, #40903, #38350) describing what reporters believe is a server-side quota-calculation regression, not a workflow problem. HN comments independently corroborate a wide spread in real-world cost experience — one user reporting session costs "regularly exceed $200" against a $200/month subscription, others describing costs in the "$5–100+/hour" range depending on workload. **Takeaway for this report:** all the token-economy levers above assume token accounting is stable and attributable to observable prompt/context/model choices; community reports suggest that at least some cost variance in Claude Code specifically is not fully explained by usage patterns and may reflect platform-side quota-accounting issues outside any orchestration rule's control. Not actionable as a rule change, but worth flagging so cost anomalies aren't automatically assumed to be a workflow mistake.

**Model/effort selection (AGREES, no new information).**
- Every practitioner source converged on the same ordering already in this report's §2 and in the existing codified rules: cheap/mechanical → Haiku, routine → Sonnet, complex/architectural → Opus only when justified, and lower `effort` for straightforward tasks. KDnuggets adds one quantified data point worth keeping in mind when justifying an Opus escalation: *"Opus costs 5x more than Sonnet per token."* No changes recommended here — community practice simply confirms the existing tiering is directionally sound.
